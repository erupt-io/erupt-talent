# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, ...) when working with code in this repository.

## Commands

```bash
# Run the application: http://localhost:8080, erupt / erupt
mvn spring-boot:run
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8099

# Run on MySQL (credentials come from the environment only: MYSQL_USER, MYSQL_PASSWORD)
mvn spring-boot:run -Dspring-boot.run.arguments=--spring.profiles.active=mysql

# Build / tests / a single test method
mvn clean package
mvn test
mvn test -Dtest=ResumeParserTest#parsesLabelledResumeBody
```

Java 17, system `mvn` (no wrapper), parent `spring-boot-starter-parent` 3.5.16. The only test class is
`ResumeParserTest`, a plain JUnit test of the resume parsing heuristics (no Spring context); nothing else
is covered by tests.

erupt comes in at `erupt.version` 2.2.0 in `pom.xml` (README.md still says 2.1.0; the pom is
authoritative). If that version does not resolve, README.md says to install it from the erupt source repo:
`mvn install -DskipTests -pl erupt-starter/erupt-spring-boot-starter,erupt-plugin/erupt-job,erupt-plugin/erupt-notice -am`.

## What this is

A runnable Spring Boot application (`xyz.erupt.talent.TalentApplication`), not a library: a recruitment
system covering resume, screening, multi-round interviews, offer approval and delivery, candidate reply,
onboarding and a funnel dashboard. The UI is generated by erupt annotations; the only frontend file is the
dashboard template `src/main/resources/tpl/talent-dashboard.ftl`.

erupt modules used: `erupt-spring-boot-starter`, `erupt-job` (scheduled jobs), `erupt-notice` (in-app
notifications), `erupt-monitor`. Also `spring-boot-starter-mail` (IMAP fetch, SMTP send), `freemarker`
(dashboard template engine), `pdfbox` plus POI from erupt (resume text extraction).

## Architecture

- **Registration and seeding.** `EruptTalentAutoConfiguration` is a `@Configuration` found by component
  scan (there is no `AutoConfiguration.imports`); it implements `EruptModule` and builds the menu tree in
  `initMenus()` (root `$talent`, the dashboard as a TPL menu, `TalentSetting` as a FORM menu).
  `TalentInitializer` runs on `ApplicationReadyEvent`, after upms has created the menus, and idempotently
  seeds the notice scenes, the settings row, two `EruptJob` rows and the roles `TALENT_HR` and
  `TALENT_INTERVIEWER` with their menus. Each step runs in its own transaction and a failing step is
  logged, never fatal.
- **Models (`model/`, tables `r_*`).** `JobPost`, `Resume`, `Interview`, `Offer`, `Onboarding`,
  `TalentTrace` (read-only audit trail), `TalentSetting` (single-record form: IMAP, SMTP, DingTalk, offer
  template and risk switches), `TalentMailbox` (one IMAP mailbox per HR), `TalentSeq`. `model/form/` holds
  the input forms of row operations. Business enums in `constant/` implement `LabeledEnum`, which turns
  them into choice options.
- **State machine in services.** `Resume.status`, `Offer.status` and `Onboarding.status` are
  `@Readonly(allowChange = false)`; they only move through `service/ResumeFlowService`,
  `InterviewFlowService`, `OfferFlowService` and `OnboardFlowService`, triggered by the row-operation
  handlers in `handler/` and the `DataProxy` classes in `proxy/`. Every change is written by
  `TraceService` to `TalentTrace`. The one exception, the resume status fix, is admin-only and requires a
  reason. `SeqService` issues the numbers (prefix + yyyyMMdd) under a pessimistic row lock in its own
  transaction.
- **Permissions.** `service/TalentAuth` holds the role checks (admin > HR > interviewer > none).
  `proxy/` contains the `PowerHandler`s (`AdminOnlyPower`, `HrOnlyPower`, `InterviewPower`), the row
  filters (`CreatorFilter`, `OwnInterviewFilter`) and `HrOnlyReadonly`; interviewers see only their own
  interviews and may fill in score, comment and conclusion only.
- **External systems, all configured in the admin, not in `application.yml`.** IMAP resume fetch
  (`job/MailFetchJob` → `MailFetchService` + `ResumeParser`), SMTP offer mail (`MailSendService`),
  DingTalk calendar (`DingTalkService`). Their secrets are `EditType.PASSWORD` fields of `TalentSetting` /
  `TalentMailbox`; `TalentSettingProxy` keeps the stored value when the mask or an empty value comes back.
  Never log or export them, and refer to them by field name only. Offer template variables are HTML
  escaped on substitution because candidate data may come from parsed mail.
- **Failure isolation.** A DingTalk sync failure is recorded on the interview and does not block it; a
  failed offer mail leaves the offer in "pending send" with a resend button instead of rolling back the
  approval; `NotifyService` runs in its own transaction, swallows errors and builds a synthetic user
  context for scheduled jobs.
- **Dashboard.** `tpl/TalentDashboardTpl` (`@EruptTpl`) renders the page; `controller/TalentDashboardController`
  serves the metrics and CSV export under the erupt API prefix + `/talent`, login required, restricted to
  HR and administrators (`DashboardService`).

## Local data and configuration

`src/main/resources/application.yml`: the default profile uses an H2 file database at `./data/talent` and
stores attachments under `./data/attachment` (`erupt.upload-path`); the `mysql` profile reads
`MYSQL_USER` / `MYSQL_PASSWORD`. `erupt.default-locales` is `zh-CN`: menu names and `@Erupt` /
`@EruptField` titles are written in Chinese and there is no i18n CSV; code comments are English. The
`.gitignore` in this repo does not list `target/`, `data/` or `.erupt/`.

## Pitfalls recorded in README.md

- The JS expression of `@Dynamic(condition = ...)` has a single variable, `value` (the dependent field's
  value); using a field name throws `ReferenceError` on save.
- With `hibernate.globally_quoted_identifiers=true`, `@Column(columnDefinition = "text")` gets quoted
  into a type H2 does not know; large text fields use `@Lob` only.
- The IMAP fetch and the DingTalk calendar were not verified end to end (they need real credentials).
  Interviewer lookup in DingTalk relies on `EruptUser.phone`.
